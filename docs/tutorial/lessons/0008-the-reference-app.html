The reference app

The house purchase read as an integration test of Lessons 1–7: a state schema with no position, guards that encode sequencing as data, mock providers that are deliberately unhelpful, and wiring that shows the whole of what an app owes the framework.

state.tsA schema with no "where we are"

The state file's header makes the framework's bet concrete: no status field, no stage, no current-step pointer. Two implementation disciplines follow from float, and both are visible in the schema itself:

  • Every field is defaulted — "that is not tidiness: a case created under an earlier definition set and read by a later one must parse." The zod .default(…) calls are the schema-side half of the ?? fallback totality discipline.
  • Outcomes are state. purchase.closedAt and purchase.deedRecordedAt are ordinary nullable strings read by ordinary conditions — which is what lets post-completion work be ordinary guarded steps.

The file also holds the domain's shared rules, and one of them demonstrates an anti-drift idiom worth naming. arrivedAmount — which money counts as arrived — is used by both the close guard's funded condition and the dev console's wire levers: "the single counting rule … stated here once so a console can never disagree with the guard about whose money is in." When a UI needs to predict what a guard will say, the prediction and the guard must share a function, never a copy.

steps.tsSequencing, exceptions, and endings — all as guards

Lesson 1 showed the linear stretch. The back half of the file is where the framework's harder claims get tested. The close guard is the richest single guard in the repo — including the codebase's one production anyOf, used for a genuine business disjunction:

The wire-reconciliation "exception path" is the claim under test: record-wire classifies each wire at the same commit that records it (matched / short / over / wrong-account), and each bad outcome has its own resolution step, scoped over exactly the wires bearing it. "No branch is drawn anywhere; the exception paths are simply steps that become available when their facts are true." The three resolutions come from one factory, and even their permits encode a judgement — returning money is the escrow officer's mechanics, but accepting a short wire is the organizer's deal concession, because it is what shortClosePermitted reads.

purchase.ts / services.tsBinding at definition time, providers that misbehave on purpose

The case type is built by a factory that takes the providers its handlers call — "binding happens here, at definition time — two apps in one process each get definitions wired to their own providers, with no shared registry to rebind and no install-before-execute ordering rule." Note also what the factory's header repeats: the definition set has no "finished" declaration, because the framework has no slot for one.

app.tsThe whole of what an app has to do

The wiring function is the framework's embedding story in one place: bootstrap the schema, build the providers, register the case type, say what ingestion runs as, mount the adapter:

Three details reward attention:

  • The ingestion actor mapping is the hook from Lesson 6 in use: events run as { id: 'system:escrow', roles: ['integration', …] } so this app's permits conditions (isIntegration) read their own shape, not a framework marker.
  • One authorization rule lives in the host, and the comment argues why: creating a case takes the organizer role, enforced by middleware at the mount — "case creation has no guard for a permits to live in — who may start a matter is the host's decision, so it sits here in the wiring, not in the framework."
  • The dev console is quarantined under /dev, with its leaks recorded. GET /dev/cases queries the framework's own table because the engine deliberately has no list read ("apps own their read models") — the comment brands it "a recorded leak, acceptable only under /dev". The case-purge route iterates CASE_TABLES because "a private copy went stale once already, leaving deleted cases' ingested_events behind, and those leftover dedup rows suppressed future deliveries that quoted the same identifiers." Even the world panel predicts webhook routing with routedStep — the framework's own rule — "so the panel's prediction of where a webhook lands cannot drift from what ingest will do."

That last bullet is the course's closing theme in miniature: everywhere two components could hold separate copies of one rule — a guard and a console, a router and a link builder, a serializer and a policy — this codebase makes them share the single implementation, and writes down the one time it didn't and got burned.
