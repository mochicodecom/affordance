The execution lifecycle

Everything in execution/: the port that makes the lifecycle testable, the claim's takeover logic, the retry loop, the commit's one decisive check, and the journal that remembers all of it.

Lesson 1 showed the skeleton — claim → run → commit, two short transactions with the handler outside both. This lesson fills in the machinery around that skeleton, which is where most of the module's care actually went: what happens when a handler crashes, when a lease expires, when an attempt fails, and how every one of those moments is remembered.

port.tsThe seam the whole module stands on

The lifecycle core never touches Postgres. It runs against LifecyclePort, and the file's header is explicit about why this seam exists and — just as important — why it is not public:

The port's shape encodes the transactional structure directly. withCaseLock means "one short transaction holding the case row's lock" — the claim and the commit are each exactly one of those — and everything else (heartbeat, retry journaling, release) deliberately runs outside any transaction:

In the pg adapter, the lease verbs are wrapped in .catch(() => undefined) — best-effort by contract. A missed heartbeat just lets the claim age; correctness never depends on a beat landing, only on the commit-time holder check. One more deliberate choice hides in the SQL: lease expiry is computed as now() + $ttl in Postgres and compared as expires_at <= now() — the storage's clock, the one clock all competing processes share, never the engine's injected now.

Time on the process side gets the same seam treatment. timers.ts is two verbs — sleep (the retry delay) and every (the heartbeat) — so the lifecycle's tests drive elapsed time virtually instead of sleeping through it. Even here there is a considered line: the retry sleep is deliberately not unref'd (a retry delay is work in progress; exiting during one abandons a claimed execution), while the heartbeat interval is (a heartbeat alone should never hold the process open).

claimBusy, or takeover

The first thing a claim does under the row lock is judge whatever claim already sits on the case. Live means busy; expired means a crashed handler's abandoned lease, and the newcomer takes the case over — journaling the abandonment as an expired entry:

There is a subtlety here that repays attention: the abandonment entry rides the claim transaction. If our own claim then fails its guard, the whole transaction rolls back — abandonment record included — and the dead lease stays in place. The comment explains why that is right: an expired lease blocks nothing, and the abandonment only becomes a fact worth recording when somebody actually took the case over.

Then comes the enforcement moment (guard re-evaluation, Lesson 2's evaluateGuard via evaluateTarget), and a refusal that is self-explaining by construction — StepNotAvailableError carries the current unmet conditions, rendered through the derived views:

Note the first constructor argument: 'step-not-available' is the refusal code, from the closed set, declared exactly where the refusal is raised. The HTTP adapter will translate codes, never classes (Lesson 7).

runThe retry loop and the handler's context

The heart of runLifecycle is a for (let attempt = 1; ; attempt += 1) loop. Two decisions shape it. First, everything an attempt registers is per-attempt — a failed attempt's onCommit writes and its end()/reopen() intent are discarded with the attempt that made them:

Second, not every failure deserves a retry. A handler that returns state its own schema rejects would return it again next attempt — a deterministic defect — so it is wrapped in an internal NonRetryable marker and fails immediately. So does ClaimLostError: once the claim is gone, retrying cannot get it back. Everything else follows the step's retry policy, journaling attempt-failed and sleeping the backoff delay between attempts:

Retries reuse the same executionId, the same claim, and the same starting state — nothing else can have moved the case, because the claim is still held. The execution id is also the handler's idempotency key: at-least-once effects on the outside world are the handler's to deduplicate, and the id is what it deduplicates on.

commitOne check, and why expired-but-undisturbed is fine

Lesson 1 showed the holder check; here is the part of its comment that usually surprises people:

Expiry is a permission for others to take over, not a deadline on us. Exclusivity comes from the claims row itself: our row still present means no takeover happened, so the commit is safe regardless of the clock. If a takeover did happen, our row is gone (replaced by the newcomer's) and the commit is refused with ClaimLostError — whose refusal code, note, is 'case-busy': to the caller, "the case moved on under you" is the same actionable answer as "the case is busy", and one an adapter can already render.

One performance note shows the codebase's habit of stating micro-decisions: the JSON Patch delta is computed before the commit transaction opens — pure CPU over the whole state document has no business running under a row lock.

journal.tsWhat is remembered, and how it is typed

Five entry kinds tell an execution's whole story: claimed, attempt-failed, completed, failed, expired. The implementation's nice move is making the field/kind pairing a type rather than prose:

Only inserts exist in the module — there is no update or delete path for a journal row anywhere in the library. And a journal append must never be the thing that fails a good execution, so serialization is total: a value that will not stringify (a cycle, a BigInt) is journaled as an { "~unserializable": … } marker rather than thrown over.

Two readers sit on top. foldExecutions assembles one record per execution from its entries — and its header preempts the obvious objection: this is folding entries of the same execution into one record, not deriving state from a log, which is the thing the design rejects. replayGuard (in replay.ts) is the audit tool: it re-runs today's definition against the journaled state, actor, and instant, and reports both evaluations side by side. A mismatch is not a bug — it is the signal that the guard changed since the execution ran. And an entry today's definitions cannot address at all is reported as unaddressable rather than thrown: replay is a sweep, so it takes the lenient side of the pair.
