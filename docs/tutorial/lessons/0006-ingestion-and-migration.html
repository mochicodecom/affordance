Ingestion and migration

The two subsystems that run steps with nobody at the keyboard — both built as filters over Lesson 3's system runner, each with a discipline against silent loss.

correlation.tsThe mapping, written in the same commit

An e-sign provider knows envelope env_9f2; it does not know case 4b0e… or that the envelope is buyer #7's agreement. The correlation registry holds that mapping, and the load-bearing decision is when it gets written:

Recall from Lesson 4 that ctx.correlate is just an onCommit write. The consequence is an invariant no code has to check: "sent but unroutable" is unrepresentable, because the sending's state write and the mapping are one transaction. Storage-wise, registration upserts on (system, externalId) — a retried handler attempt registering the same envelope again "is not an error, it is the same fact."

ingest.tsDedup, correlate, execute — and never a quiet drop

The module header states the contract in one paragraph, worth reading verbatim:

Dedup: a unique insert, not a lookup

Providers deliver at-least-once, so dedup is the front door — and it is a unique insert, "not a lookup-then-insert, which races itself":

Exactly one of N concurrent deliveries inserts; the losers read what the winner wrote and answer duplicate. The idempotency key has a considered structure: its fixed prefix is (system, externalId, type) — the same notification about the same envelope produces the same key however often it is delivered — and the tail is the provider's own delivery id, or a payload hash when the provider cannot say which delivery this is ("content-addressed dedup, which is the best anyone can do").

The subtle case is a redelivery of a dead-lettered event. Should the provider's retry get another chance? The answer is a total table over the reason codes — total on purpose, "so a new code cannot be added without deciding its reopen policy":

Transient outcomes reopen; deterministic ones stay dead — "it will be refused the same way on every retry, so reopening it would only invite endless redelivery."

Execute: no privileged path

A routed event executes through runAsSystem — the ordinary claim → run → commit, with the external system as the journaled actor. Ingestion has no back door; the guard still decides, transactionally. Notice what this means for the closed code set: the dead-letter reasons are not a parallel taxonomy that could drift — apart from ingestion's own two (unrouted, no-step), every reason is the AffordanceErrorCode the refused execution already declared at its raise site, projected. A new refusal class can never misroute here, because nothing here switches on classes.

One more habit worth stealing: the local deadLetter helper both settles the row and builds the caller's result from the same fields — "one helper, so a branch cannot record one thing and report another."

migrate.tsThe escape hatch that is not a second way of working

Float handles additive change; a genuine restructure (rename, split, scalar-to-collection) defeats any fallback expression. The migration module's two properties keep it an escape hatch rather than a parallel mechanism:

  1. A migration is an execution. The transform runs as a synthetic step named migrate:<name> through the ordinary lifecycle — case row lock, claim, schema validation, journal entry all apply unchanged. An auditor asking "why did this case's shape change in March" gets the same kind of answer as for anything else.
  2. The journal is the marker. A case has been migrated iff it carries a completed migrate:<name> entry. No bookkeeping table, no flag in app state — so re-running is a no-op by construction, and an interrupted run resumes where it stopped.

The step is spliced into a view of the case type for the duration of the run (the real definition is untouched, so no client ever sees it as an affordance), and handed to runAsSystem via its definition override — the option that exists "so no sweep has to smuggle a definition in by rewriting caseTypeFor".

The sweep

Candidate selection is one SQL predicate — the marker check pushed into the database, which is also what makes two concurrent runs of the same migration safe (a case migrated by the other instance simply is not returned):

Per case, the sweep is a textbook filter over the system runner's total outcome: a commit advances the case; a settled run — a held claim, a throwing transform, a result its schema rejects — is reported as a failure and no marker is written, so the next run picks the case up again. Failures never stop the run.

Two smaller decisions complete the picture. A case the transform leaves identical is still journaled (and so still marked) — "'this migration considered this case and had nothing to do' is a fact worth being able to prove." And dryRun needs no claim, no lock, and no write, because the transform is pure — it reads state through the lenient resolver (resolveStoredState, Lesson 5) and reports the would-be deltas, leaving no marker so the real run still has every case to do.
