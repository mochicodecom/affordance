The HTTP adapter

@affordance/http in four files: a framework-agnostic router, one route grammar with two readers, the closed refusal codes turned into statuses, and the audience module that decides what ever leaves the process.

api.tsA router that knows no HTTP library

The adapter core routes over plain shapes — { method, path, query, body, actor } in, { status, body } out. No Request, no Response, nothing from any HTTP library. The payoff is stated up front, and hono.ts exists mostly to prove it: a binding for hono, express, Lambda, or a test harness is a translation of those two shapes and nothing else.

The seam carries a second responsibility that is easy to miss: actor resolution lives on the host side of it. The binding resolves whatever the app calls an actor (from its session middleware, its tokens) and puts the value on the request; the framework never sees a header. From there down, the actor is opaque — passed verbatim to conditions, journaled verbatim, used verbatim for visibility.

The adapter also refuses to depend on the whole engine:

errorsCodes to statuses — and the two halves of one rule

Lesson 3 showed refusals declaring a code at their raise site. Here is the payoff. The adapter's entire error policy is one total map plus one translation function:

Two symmetric rules meet here, and the code comments name them as halves of one thing:

  • A crash is never answered as a refusal. Anything that is not an AffordanceError — a bug, the database being gone — is rethrown, not turned into a tidy response.
  • A caller's mistake is never surfaced as a crash. Malformed caller input found while reading the request (a bad asOf, a non-integer limit, an unknown journal entry kind) is thrown as the framework's own bad-request refusal, so the same single translator answers it with a 400.

Because Record<AffordanceErrorCode, number> is total, adding a refusal code to the contract without deciding its status is a compile error in this file. That is the closed-set promise from the architecture doc, mechanized: "a refusal the adapter has never heard of is impossible rather than a 500."

contract.tsOne grammar, two readers

The route table lives in the contract module, and both the link builder (which fills patterns into hrefs) and the dispatcher (which matches request paths against them) are filters over it — "a link the contract hands out is parseable by construction":

The serializers around it produce every byte any route puts on the wire, translating core records into @affordance/contract's payload types — which live in a dependency-free package so a client reads against them without acquiring the engine. The translation is deliberately field-by-field even where the types are structurally identical today: "assignability covers renames but not additions — a field core grows would otherwise pass silently onto every surface this module exists to police."

Three route-level decisions carry design weight:

  • POST /events answers 200 for any event it recorded, whatever became of it — "a 5xx teaches the provider to retry something that will never succeed." The dead-letter surface is where outcomes are read (Lesson 6).
  • asOf is accepted on reads only. The affordances route allows read-only time travel ("what was possible last Tuesday"), but the execute route deliberately does not: "evaluating a claim as of an instant the caller chose would let the caller get past a time condition."
  • Create answers from the handle in hand. createCase responds with affordancesOf(created) — no second load: "the row was written and validated one statement ago, so a re-read would only fetch back the same data."

audience.tsThe one module that decides what a caller may be told

This is the sharpest file in the package, and its premise is a security observation: permits conditions encode internal policy — role names, thresholds, approval hierarchies — and naming the one a caller failed tells them exactly what to fake to pass it. So under the default permitted visibility, no permits result ever leaves the process: not in a blocked entry, not in an explanation, not in a refusal, and not in a journal entry's recorded guard.

The rule has record-sized consequences, each decided here and nowhere else:

FunctionWhat the default audience loses
visibleConditions / visibleGuardEvery permits condition result. The verdict pair (possible/permitted) survives — "not you" is an honest answer — but never which rule decided it.
visibleAffordancesBlocked entries this actor is not permitted — which is where other actors' tracks disappear: a buyer's payload contains their own track and nothing else, without the app writing a filter.
visibleJournalEntryThe recorded case state — operator-only. And it is absent, not null: "a null would read as 'the evidence was empty' where the truth is 'not yours to read'."
visibleRefusalThe refusal's prose itself is rebuilt from the visible conditions only — the framework's own message names everything, "which is right for a server log and wrong for a response body."

And the structural argument for why the rule lives in one module, from the header — perhaps the best single statement of the codebase's review philosophy:
