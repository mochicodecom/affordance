The shape of the implementation

A map of the code as it actually is: five packages, seven core subsystems, one end-to-end trace, and the handful of idioms the whole codebase is written in.

You already know what the framework claims — no stored position, guards over state, claim → run → commit. This lesson is about where those claims live in the source and what the code that makes them true looks like. By the end you should be able to open packages/core/src and know what every directory owes you before reading a line of it.

Section 1Five packages, one direction

The repo is a pnpm workspace. Dependencies point one way — down toward core — and contract deliberately depends on nothing, because it is the piece a client compiles against without ever touching the engine:

reference-app ──► @affordance/http ──► @affordance/core
      │                  │
      └──────────► @affordance/contract ◄── (ui reads payloads against it)

@affordance/testkit — dev-only Postgres test setup, shared by the pg suites

core is the framework: a TypeScript library embedded in the app, persisting to the app's own Postgres. http is an adapter that serves the affordance/v1 wire contract and treats the engine as a port. reference-app is a full house-purchase application that exists to prove the framework's claims under test — its steps.ts is the best real-world reading of the authoring API.

Stop 2 — The guard walk (guards/guard.ts)

A guard is two flat AND-maps (requires, permits) whose entries are conditions or one level of named anyOf. The implementation's key move is that exactly one function knows this shape — guardEntries — and everything else is a filter over its output:

Each entry comes back with its stable condition address — requires.escrowReady, or requires.financing.preApproved for an anyOf arm — which is the name refusals, explain, and the journal all use. The same walk is also what step() uses to validate definitions, so by construction a definition that step() accepts is one evaluateGuard can read.

The database touch and the computation are never interleaved.

Stop 4 — The lifecycle (execution/execute.ts)

The claim is one short transaction under the case row's lock — load, take over any expired lease, resolve the step target, validate input, re-evaluate the guard (the enforcement moment), insert the lease, journal claimed. Note what gets journaled: the guard evaluation and the state it ran against, so audit is exact rather than re-derived:

The handler then runs with no transaction open, kept exclusive by the lease plus a heartbeat. The commit re-takes the row lock and performs the one check that makes a stale write impossible:

One more structural fact, easy to miss: the lifecycle core, runLifecycle, never touches Postgres. It talks to a narrow internal interface, LifecyclePort (execution/port.ts). executeStep binds it to the pg port; the lifecycle's own tests bind it to an in-memory port and drive time through fake timers. The port is not exported — it exists for testability, not as a storage abstraction.

Section 4The idioms, once you know to look

Section 3's trace already showed most of the codebase's recurring moves. The full list is on the codebase map; the two you will meet in every remaining lesson are:

One walk, many filters. guardEntries was the first instance. The same discipline repeats wherever two readers could drift apart: scope fan-out is one function (selectTargets) that every listing filters; addressing is one function (addressTarget) whose loud filter is resolveTarget and whose lenient filter is audit replay.

Lenient / loud pairs. Wherever old data can defeat the engine, there are exactly two resolutions and which one you get is part of the interface: a sweep is lenient (an unreadable case contributes nothing and the sweep continues), an addressed request is loud (you named a case and a step; silence would be a wrong answer, so it throws). For running steps, the loud half is Engine.execute and the lenient half is drawn once as the system runner:

Ingestion and migration are both filters over this one outcome type — which is exactly the shape you should expect by now.
