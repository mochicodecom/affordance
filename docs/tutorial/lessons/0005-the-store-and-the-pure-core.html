The store and the pure core

The bottom and the top of the engine in one lesson: how Postgres is held (the Queryable seam, the schema, a bootstrap that yields to live work), and the pure computation the whole load-then-compute pattern feeds.

store.ts / resolve.tsLoad, resolve, validate — spelled once

Every read path needs the same three moves in the same order: load the row, resolve case_type against the registered definitions, validate the stored document against that definition's schema. The order is forced by the data — the schema to validate against is only knowable from the row — which is why the untyped loader exists and why its doc comment reads like a warning label:

resolve.ts packages the three moves as the interface, and — by now you can predict this — it is a lenient/loud pair:

  • resolveCase / resolveCaseForUpdate are loud. Their callers were handed a case id and owe an answer about that case; a stored document that no longer validates is an app bug and says so (CaseStateValidationError).
  • resolveStoredState is lenient. Its callers sweep (migration scanning a case type); an unreadable case contributes nothing. One detail shows the care level: it returns { state } | null — wrapped in an object — because a perfectly valid case state may legitimately be null, and a sweep must not confuse the two.

resolveCaseForUpdate uses select … for update, and its comment names what that row lock actually is: the execution lifecycle's serialization point. The claim and the commit both take it first, which is what makes "exactly one of N concurrent attempts claims" and the takeover decision things no two transactions can decide concurrently.

Ids, in passing, are minted as kind:uuid — case:…, execution:… — self-describing wherever they travel (a log line, a support ticket). The prefix is for humans; equality is the only operation ids support, and nothing anywhere parses one apart.

bootstrap.tsDDL that yields to live work

The schema is five tables in a dedicated affordance Postgres schema (so named because case is a SQL reserved word): cases, journal, claims, correlations, ingested_events. Two rows of the DDL are whole design decisions in one constraint each:

ConstraintWhat it is
claims.case_id text primary key"One in-flight execution per case" — the serialization rule as a table constraint, not code.
ingested_events.idempotency_key unique"Three deliveries, one execution" — webhook dedup as a database fact rather than a hope (Lesson 6).

bootstrap() is called on every app start, and the interesting engineering is in making that safe against a busy database. The header states the trap precisely:

Three defenses stack: a schema_version check first (the common case takes no locks at all); a pg_advisory_xact_lock serializing concurrent bootstraps; and — inside the DDL itself — set local lock_timeout = '2s', so when there is work and it collides with live commits, the bootstrap is the transaction that yields, and the retry loop (which retries only on deadlock/lock-timeout/serialization codes) tries again. Schema management yields to live work, never the reverse.

One export is a small masterclass in preventing drift: CASE_TABLES, the list of per-case tables in child-first deletion order, exists so a consumer that sweeps per-case rows (a console's purge, a test harness) iterates it "instead of keeping a private copy that goes stale the release a table is added". The one answer to "which tables does the framework own", outside the DDL itself.
