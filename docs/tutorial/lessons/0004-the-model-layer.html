The model layer

How case types and steps are engineered: the type-level tricks behind annotation-free authoring, the erasure boundary, and the step-target machinery that every other subsystem consumes.

The model/ module is the authoring API plus one crucial piece of shared machinery — step targeting. Lesson 1 showed what authoring looks like; this lesson explains how it is made to work, and then walks target.ts, which is the file the claim, explain, the affordance listing, and audit replay all stand on.

casetype.tsTwo declarations, and one honest any

A case type is a name, a state schema, and a list of steps — with loud construction-time validation (duplicate step names throw, because they would make affordance identity (step × scope key) ambiguous). When reviewing changes, this is the standard to hold any new any to: is it re-anchored at every use, and does its comment say so?

step.ts / scope.tsHow annotation-free authoring works

The reference app writes conditions like requires: { purchaseOpen } with no type annotations anywhere in the step call. Three mechanisms combine to make that inference work:

  1. The state type comes from the schema value. stepsOf(PurchaseState, …) derives TState as StandardSchemaV1.InferOutput<S> — the same derivation caseType performs. Factory and case type are anchored to one declaration and cannot drift: the state a condition sees is definitionally the state the engine validates against.
  2. The actor type is named by a value-level marker. TypeScript has no partial type-argument inference — spelling stepsOf<…, PurchaseActor> would force spelling the schema's type too. So the actor type rides a phantom-typed value instead:
  1. Overload ordering carries the scoped/unscoped split. step() declares the scoped overload first and discriminates on the presence of scope; a scoped step's element type anchors on scope.select alone, which is why ctx.scope arrives fully typed, with no undefined to narrow away.

All of that richness then collapses. The scoped condition maps are erased to the guards module's shape with a single commented cast — sound because evaluation of a scoped guard always binds scope, which the scoped types require:

This is the erasure idiom in full: authoring types are precise, machine types are erased, and every cast between them is singular, commented, and justified by an invariant the runtime maintains. There are exactly three such casts in the model layer — the handler, the scoped condition maps, and the registry's AnyCaseType.

target.tsThe machinery everyone stands on

A step target is a step plus its scope binding, resolved against a given case state — the pair an affordance's identity names. The file's header states its design in two rules, and they are the lenient/loud pair made concrete:

  • A defective selector is a selection failure. A scope.select that throws over historical state (a totality bug) yields { targets: [], failure: { reason } }. Each caller decides what its audience deserves: the listing renders a blocked $scope entry, a sweep skips the step, resolveTarget throws.
  • A key integrity violation is loud everywhere. Duplicate or malformed scope keys corrupt affordance identity itself — the thing journal entries and refusals name — so ScopeKeyError propagates through every path. No caller may absorb it into "no targets":

Addressing — "step X, element K, on this state" — is the second single implementation. addressTarget answers with the target or a failure that names its kind, and the kinds are a discriminated union, so filters can treat one differently without re-deriving how the address failed:

Each failure carries the error the loud filter would throw, so the diagnosis — including helpful details like the currently-valid scope keys — is constructed exactly once and reads identically whether thrown at a caller or reported by a sweep. The filters over it:

FilterPolicyWhy
resolveTarget (the claim, explain's addressing)Loud — throws failure.errorAn addressed caller named a case and a step and is owed an answer about those.
Audit replay (replayGuard)Lenient — reports unaddressableA sweep over the journal; one drifted entry must not take down the audit of the rest.
explain, one special caseAnswers a defective-selectorThe listing published that exact link as a blocked entry, so the probe deserves an answer, not a throw.

Finally, evaluateTarget is the single evaluation shared by explain and the claim — "so the enforcement moment and the explanation of it can never drift apart". Notice also that a StepTarget carries the state it was resolved against; a binding can never be evaluated against a different document than the one that produced it.

handler.tsThe commit-write seam

One type from handler.ts completes the picture from Lesson 3. ctx.onCommit registers a CommitWrite — a callback that receives the framework's own commit transaction:

This is how the app gets transactional atomicity with the framework without the framework holding a transaction across the handler. The handler runs free; only the writes it registered are replayed inside the commit. A CommitWrite that throws aborts the whole commit and the attempt is journaled as failed — the app's writes get the same all-or-nothing deal as the case row and the journal entry. ctx.correlate (Lesson 6) is just a CommitWrite in disguise.
