Guards: one walk, one answer

The guards module in full: how the condition contract is enforced by types, how the algebra stays small, and how one evaluation record feeds every consumer — listings, explain, refusals, and the journal.

The module is four files, and their division of labor is clean: condition.ts states the contract of a single condition, guard.ts owns the algebra and its single walk, evaluate.ts turns a guard plus a context into the evaluation record, and time.ts normalizes instants. This lesson reads them in that order.

condition.tsThe contract, enforced where possible

A condition is one named, pure, synchronous predicate. The interesting part of the implementation is which of those properties are enforced by types and which are left as documented discipline:

  • Synchronous — enforced by type. An async condition returns a Promise, which is not assignable to ConditionOutcome. Compile error, not a lint rule.
  • Clock-free — enforced by omission. ConditionContext carries actor and (for scoped steps) scope, and deliberately no clock. Nothing stops a condition from calling Date.now(), but the interface offers no time, and evaluation takes an explicit asOf.
  • Total over historical state — discipline only. The doc comment states the s.split?.confirmed ?? false rule; types cannot enforce it, so the runtime absorbs violations instead (below).

The { ok, reason } verdict form is why the reference app's conditions read the way they do — the reason string travels verbatim into evaluation records, explain output, and the journal.

Note the 'unknown' kind. The walk is total: a malformed entry (something that is neither a function nor an anyOf group) is classified and reported — the walk itself never throws. What happens to an 'unknown' entry then depends on who is filtering the walk — and this is the design's punchline:

  • step() filters it into a deploy failure. Definition-time validation walks the guard and throws TypeError on any non-condition, non-anyOf entry.
  • evaluateGuard filters it into a failed condition. If a malformed entry somehow reaches evaluation, it becomes passed: false with the reason "entry is not a condition function or an anyOf(...) group" — one bad entry degrades one answer, never the case.

Same walk, two policies, and no third reader that could quietly disagree.

evaluate.tsThe evaluation record

evaluateGuard(guard, ctx) produces one plain, JSON-serializable object that the rest of the engine leans on. Its guarantees are stated in the header and worth memorizing, because they are what everything downstream assumes:

  • Pure and deterministic — no I/O, no ambient clock; same (guard, state, actor, asOf), same record.
  • Complete — every condition and every anyOf arm is evaluated and reported. There is no short-circuiting, so "why not?" is always answerable in full, and a passing anyOf shows which arm carried it.
  • Total — a condition that throws (usually a totality bug against sparse historical state) becomes a failed result whose reason is the thrown message.
  • Serializable — the record goes into the journal's guard-results field verbatim.

time.tsThe lenient/loud pair, applied to instants

The smallest file in the module is a textbook instance of the codebase's central idiom. Two functions, same job, opposite failure policies — and which one you get is part of the interface:
